## Node.js의 싱글스레드 아키텍처란?
Node.js는 싱글스레드 기반으로 동작하는 런타임이지만, 동시에 비동기 I/O 처리를 위한 이벤트 루프 메커니즘을 활용한다. 많은 개발자들이 "Node.js는 싱글스레드다"라는 말에 혼란을 느끼는데, 실제로는 백그라운드에서 여러 스레드를 활용하고 있기 때문이다.

Node.js의 핵심 구성 요소는 다음과 같다
- **V8 JavaScript 엔진**: JavaScript 코드 실행을 담당
- **libuv**: 비동기 I/O 작업과 이벤트 루프 관리
- **메인 스레드**: JavaScript 코드 실행과 이벤트 루프가 동작하는 단일 스레드
- **이벤트 루프**: 비동기 작업 스케줄링과 콜백 처리 담당

간단한 다이어그램으로 표현하면 아래와 같다.
```
┌───────────────────────────┐
│           Node.js         │
│    ┌─────────────────┐    │
│    │   메인 스레드   │    │
│    │ ┌─────────────┐ │    │
│    │ │ 이벤트 루프  │ │    │
│    │ └─────────────┘ │    │
│    └─────────────────┘    │
│            │              │
│    ┌───────┼───────┐      │
│    │       │       │      │
│    ▼       ▼       ▼      │
│  ┌─────┐ ┌─────┐ ┌─────┐  │
│  │libuv│ │네트워크│ │FS │  │

└───────────────────────────┘
```

## 이벤트 루프의 역할
이벤트 루프는 Node.js의 핵심 메커니즘으로, 여러 단계(페이즈)로 구성되어 있다
1. **timers**: setTimeout(), setInterval() 콜백 실행
2. **pending callbacks**: 지연된 I/O 콜백 실행
3. **idle, prepare**: 내부 사용 단계
4. **poll**: 새로운 I/O 이벤트 가져오기, I/O 관련 콜백 실행
5. **check**: setImmediate() 콜백 실행
6. **close callbacks**: 소켓 등의 종료 콜백 실행

각 단계는 FIFO 큐를 가지고 있어 해당 단계에 등록된 콜백들을 순차적으로 처리한다. 아래는 간단한 이벤트 루프 기반 비동기 코드 예시다.

```javascript
const fs = require('fs');

console.log('시작');
fs.readFile('example.txt', 'utf8', (err, data) => {
  if (err) throw err;
  console.log('파일 내용:', data);
});
console.log('다음 작업 진행');
```
위 코드에서 파일 읽기 작업은 비동기적으로 처리되며, 콜백 함수는 작업이 완료된 후 이벤트 루프의 적절한 단계에서 실행된다.

## libuv와 백그라운드 스레드 처리
### libuv의 역할
libuv는 Node.js의 비동기 I/O를 구현하는 C 라이브러리로, 다음과 같은 역할을 수행한다.
- 이벤트 루프 구현
- 비동기 파일 I/O, DNS 작업, 네트워크 I/O 등 처리
- OS별 비동기 API 추상화 (Windows: IOCP, Linux: epoll, macOS: kqueue)
- 스레드 풀 관리

### libuv 스레드 풀 작동 방식
libuv는 기본적으로 4개의 스레드로 구성된 스레드 풀을 생성한다(환경 변수 UV_THREADPOOL_SIZE로 최대 128개까지 조정 가능)
- **커널 지원 작업**: 네트워크 I/O와 같이 OS 커널이 비동기 작업을 지원하는 경우, libuv는 커널에 직접 작업을 위임
- **커널 미지원 작업**: 파일 시스템 작업, DNS 조회, 암호화 작업 등 커널이 비동기를 지원하지 않는 작업은 스레드 풀에서 처리

```
┌──────────────────────────────────────────────────────┐
│                    Node.js 프로세스                   │
│                                                      │
│  ┌───────────────────┐      ┌─────────────────────┐  │
│  │     메인 스레드    │      │     libuv 구성요소   │  │
│  │  ┌─────────────┐  │      │                     │  │
│  │  │ JavaScript  │  │      │  ┌───────────────┐  │  │

│                             │  │  스레드 풀    │  │  │

```

### 비동기 작업 처리 과정
1. JavaScript에서 비동기 API 호출 (예: fs.readFile())
2. libuv에서 해당 작업이 OS 커널에서 비동기적으로 처리 가능한지 확인
3. 가능하면 OS 커널 API 활용, 불가능하면 스레드 풀에 작업 위임
4. 작업 완료 시 결과를 콜백 함수와 함께 이벤트 루프의 해당 단계 큐에 등록
5. 이벤트 루프가 해당 단계에 도달하면 등록된 콜백 실행

## 전통적인 멀티스레딩 모델과의 비교
### 전통적인 멀티스레딩 모델 (예: Java)
전통적인 멀티스레딩 서버 아키텍처(예: Java Servlet)는 다음과 같은 특징을 가진다.
- **스레드 풀 기반**: 요청마다 스레드를 할당하는 방식
- **블로킹 I/O**: 스레드가 I/O 완료될 때까지 블로킹됨
- **공유 상태**: 모든 스레드가 같은 메모리 공간에 접근 가능
- **락(Lock) 메커니즘**: 동시성 처리를 위해 락, 세마포어 등의 동기화 도구 사용
- **스레드 생성/관리 오버헤드**: 요청량에 따라 스레드 생성/소멸 오버헤드 발생

```
┌─────────────────────────────────────────┐
│         멀티스레드 서버 아키텍처         │
│                                         │
│  ┌────────┐  ┌────────┐  ┌────────┐    │
│  │스레드 1 │  │스레드 2 │  │스레드 3 │    │
│  │        │  │        │  │        │    │
│  │┌──────┐│  │┌──────┐│  │┌──────┐│    │
│  ││요청 1││  ││요청 2││  ││요청 3││    │
│  │└──────┘│  │└──────┘│  │└──────┘│    │
│  └────────┘  └────────┘  └────────┘    │
│                                         │
│  ┌────────────────────────────────┐     │
│  │          공유 메모리 영역      │     │
│  └────────────────────────────────┘     │
└─────────────────────────────────────────┘
```

### Node.js와 멀티스레딩 모델의 주요 차이점

| 구분     | 전통적 멀티스레딩                  | Node.js 싱글스레드+이벤트 루프          |
| ------ | -------------------------- | ----------------------------- |
| 스레드 관리 | 요청별 스레드 할당, 명시적 스레드 생성/관리  | 단일 메인 스레드, 백그라운드 스레드 풀 자동 관리  |
| I/O 처리 | 블로킹 I/O (스레드 대기)           | 논블로킹 I/O (이벤트 기반 콜백)          |
| 메모리 모델 | 공유 메모리, 동시성 이슈 발생 가능       | 격리된 메모리, 명시적 공유만 가능           |
| 동기화    | 락, 세마포어 등 명시적 동기화 필요       | 이벤트 루프의 단일 스레드 실행으로 동기화 이슈 감소 |
| 자원 효율성 | 스레드당 메모리 소비, 컨텍스트 스위칭 오버헤드 | 적은 메모리 소비, 컨텍스트 스위칭 최소화       |
| 확장성    | 스레드 수 증가에 따른 오버헤드 증가       | 비동기 I/O로 적은 수의 스레드로 높은 동시성 달성 |

## 전통적 멀티스레딩의 한계와 Node.js의 해결책
### 전통적 멀티스레딩의 한계
1. **스레드 생성/관리 오버헤드**:
    - 각 요청마다 스레드 생성 또는 스레드 풀에서 할당
    - 스레드 수가 증가하면 메모리 사용량 급증
    - 컨텍스트 스위칭에 따른 CPU 오버헤드 발생
2. **자원 경합과 동기화 복잡성**:
    - 공유 자원 접근 시 락(lock)을 통한 동기화 필요
    - 데드락(deadlock), 라이브락(livelock) 발생 위험
    - 동기화 로직 구현의 복잡성
3. **확장성 제한**:
    - 동시 스레드 수 증가에 따른 성능 저하
    - 메모리 소비 증가로 인한 확장 한계

### Node.js의 효율적 해결 방안
1. **이벤트 루프 기반 논블로킹 모델**:
    - 단일 스레드로 많은 동시 연결 처리 가능
    - 비동기 콜백 방식으로 I/O 대기 시간 활용
    - 스레드 생성 오버헤드 제거

javascript

```javascript
// Node.js에서 여러 요청을 동시에 처리하는 예
const http = require('http');

const server = http.createServer((req, res) => {
  // 비동기 작업
  setTimeout(() => {
    res.writeHead(200);
    res.end('Hello World');
  }, 100);
  
  // 이 사이에 다른 요청 처리 가능
});

server.listen(3000);
```

2. **libuv 스레드 풀의 효율적 활용**:
    - 필요한 경우에만 백그라운드 스레드 사용
    - OS 커널의 비동기 기능 최대한 활용
    - 제한된 수의 스레드로 많은 I/O 작업 처리
3. **컨텍스트 스위칭 최소화**:
    - 단일 스레드 이벤트 루프로 컨텍스트 스위칭 오버헤드 감소
    - CPU 자원 효율적 활용
4. **메모리 효율성**:
    - 요청당 스레드 할당 대신 이벤트 기반 처리로 메모리 효율성 증가
    - 스레드 스택 메모리 절약

## 확장된 멀티스레딩 지원: Worker Threads
Node.js는 버전 10부터 Worker Threads API를 통해 CPU 집약적인 작업을 위한 멀티스레딩 기능을 제공한다.

```javascript
const { Worker, isMainThread, parentPort } = require('worker_threads');

if (isMainThread) {
  // 메인 스레드 코드
  const worker = new Worker(__filename);
  worker.on('message', (message) => {
    console.log('워커로부터 메시지:', message);
  });
  worker.postMessage('메인에서 워커로 메시지 전송');
} else {
  // 워커 스레드 코드
  parentPort.on('message', (message) => {
    console.log('메인으로부터 메시지:', message);
    // CPU 집약적인 작업 수행
    parentPort.postMessage('작업 완료');
  });
}
```

### Worker Threads와 기존 멀티스레딩의 차이
Worker Threads는 전통적인 멀티스레딩과 다른 방식으로 구현된다.
- **격리된 실행 환경**: 각 워커는 독립적인 V8 인스턴스와 이벤트 루프를 가짐
- **메시지 전달 방식**: 공유 메모리 대신 메시지 전달(postMessage)을 통한 통신
- **명시적 공유만 허용**: ArrayBuffer와 SharedArrayBuffer를 통한 제한적 공유만 가능
- **사용자 수준 관리**: 내부 스레드 풀과 달리 개발자가 직접 생성/관리

## 개인적 의견
Node.js의 싱글스레드 논블러킹 아키텍처는 I/O 바운드 작업에 매우 효율적이라고 생각한다. 전통적인 멀티스레드 방식이 각 요청마다 스레드를 할당하는 무거운 방식이라면, Node.js는 최소한의 스레드로 최대한의 처리량을 내도록 설계되었다.

다만 CPU 집약적인 작업에서는 메인 스레드가 블로킹될 수 있어 주의가 필요하다. 이 경우 Worker Threads API를 활용하거나, 계산 집약적인 작업은 별도의 마이크로서비스로 분리하는 것이 좋은 방법이라고 생각한다.

실무에서 대규모 서비스를 구축할 때, Node.js의 이러한 특성을 잘 이해하고 있다면 적절한 상황에서 최고의 성능을 발휘할 수 있을 것이다. 특히 마이크로서비스 아키텍처에서 가벼운 API 서버로 활용하면 리소스 효율성과 처리량 측면에서 큰 장점을 얻을 수 있다.
