## 서론

현대 클라우드 네이티브 환경에서는 컨테이너화된 애플리케이션을 효율적으로 관리하기 위해 Kubernetes가 널리 사용되고 있습니다. Kubernetes의 핵심 기능 중 하나는 컨테이너 간 네트워킹을 제공하는 것입니다. 이를 위해 Kubernetes는 CNI(Container Network Interface) 플러그인 생태계를 지원하며, 그 중 Flannel은 가장 간단하고 널리 사용되는 네트워크 솔루션 중 하나입니다.

이 보고서에서는 Flannel의 아키텍처, 작동 원리, 다른 CNI 플러그인과의 비교, 그리고 실제 구현 시나리오에 대해 심층적으로 탐구합니다.

## Flannel 개요

Flannel은 CoreOS에서 개발한 오픈 소스 네트워크 플러그인으로, Kubernetes 클러스터 내에서 간단한 계층 3 네트워크를 제공합니다. Flannel의 주요 목적은 다양한 노드에 분산된 컨테이너 간의 통신을 가능하게 하는 것입니다.

### Flannel의 역사와 발전

Flannel은 2014년 CoreOS에 의해 시작된 프로젝트로, Kubernetes가 대중화되기 시작하면서 인기를 얻었습니다. CNI 스펙이 발전함에 따라 Flannel은 CNI 플러그인으로서의 기능을 확장했으며, 현재는 Kubernetes 클러스터의 기본 네트워킹 솔루션으로 널리 사용되고 있습니다.

### Flannel의 주요 특징

- **단순성**: 설치와 구성이 간편하여 초보자도 쉽게 사용 가능
- **오버레이 네트워킹**: VXLAN을 사용한 오버레이 네트워크 지원
- **경량화**: 단일 바이너리(flanneld)로 배포되어 자원 소비가 적음
- **다양한 백엔드**: VXLAN, UDP, host-gw 등 다양한 백엔드 지원
- **Kubernetes 호환성**: Kubernetes 배포 도구에서 기본적으로 지원됨

## CNI(Container Network Interface)와 Flannel

### CNI 개념 이해

CNI(Container Network Interface)는 컨테이너 런타임과 네트워크 플러그인 간의 표준 인터페이스를 정의합니다. 이를 통해 컨테이너가 생성되거나 삭제될 때 네트워크 설정을 동적으로 구성할 수 있습니다.

CNI의 주요 목적은 다음과 같습니다:

- 컨테이너에 네트워크 인터페이스 추가 및 제거
- IP 주소 할당 및 관리
- 다중 호스트 연결성 제공

### Flannel과 CNI의 관계

Flannel은 CNI 스펙을 구현한 플러그인으로, Kubernetes의 kubelet이 파드를 시작하거나 삭제할 때 Flannel CNI 플러그인을 호출하여 네트워크 리소스를 구성하거나 해제합니다. Flannel CNI 플러그인은 다음과 같은 작업을 수행합니다:

1. 파드의 네트워크 네임스페이스에 veth 인터페이스 추가
2. veth 페어의 다른 쪽을 호스트의 cni0 브리지에 연결
3. IPAM(IP Address Management) 플러그인을 호출하여 IP 주소 할당
4. 라우팅 테이블 설정

## Flannel의 아키텍처와 작동 원리

### Flannel의 전체 아키텍처

Flannel은 다음 주요 구성 요소로 이루어져 있습니다:

1. **flanneld**: 각 노드에서 실행되는 에이전트
2. **etcd/Kubernetes API**: 네트워크 구성 및 할당 정보 저장
3. **cni0 브리지**: 노드 내 파드 통신을 위한 브리지 인터페이스
4. **flannel.1**: VXLAN 트래픽을 처리하는 VTEP(VXLAN Tunnel End Point) 인터페이스

![](https://velog.velcdn.com/images%2F200ok%2Fpost%2F37c54e6e-61fd-4246-b253-4185bdf2d2eb%2Fimage.png)

### Flannel의 동작 원리

Flannel의 동작은 다음과 같은 단계로 이루어집니다:

1. **서브넷 할당**: 각 노드에 고유한 서브넷 할당 (예: 10.244.0.0/24, 10.244.1.0/24)
2. **파드 IP 할당**: 파드가 생성되면 노드의 서브넷에서 IP 주소 할당
3. **노드 내 통신**: 같은 노드의 파드는 cni0 브리지를 통해 통신
4. **노드 간 통신**: 다른 노드의 파드 간 통신은 VXLAN 캡슐화를 통해 이루어짐

### 노드 내 통신 과정:

1. 파드 A에서 같은 노드의 파드 B로 패킷 전송
2. 패킷이 파드 A의 veth 인터페이스를 통해 cni0 브리지로 전달
3. cni0 브리지가 MAC 주소 테이블을 참조하여 파드 B의 veth 인터페이스로 패킷 전달

### 노드 간 통신 과정:

1. 파드 A(노드 1)에서 파드 C(노드 2)로 패킷 전송
2. 패킷이 파드 A의 veth 인터페이스를 통해 cni0 브리지로 전달
3. 라우팅 테이블에 따라 패킷이 flannel.1 인터페이스로 전달
4. flannel.1이 패킷을 VXLAN으로 캡슐화하여 노드 2의 flannel.1로 전송
5. 노드 2의 flannel.1이 패킷을 디캡슐화하여 cni0 브리지로 전달
6. cni0 브리지가 패킷을 파드 C의 veth 인터페이스로 전달

## Flannel 백엔드 유형

Flannel은 다양한 백엔드를 지원하여 다양한 환경에서 유연하게 사용할 수 있습니다. 주요 백엔드는 다음과 같습니다:

### VXLAN (기본 백엔드)

VXLAN(Virtual Extensible LAN)은 Flannel의 기본 백엔드로, 다음과 같은 특징이 있습니다:

- UDP 8472 포트를 사용하여 패킷 캡슐화
- 커널 내장 VXLAN 모듈 사용으로 성능 최적화
- VNI(VXLAN Network Identifier) 값으로 1 사용 (Windows에서는 4096 이상)
- DirectRouting 옵션을 통해 같은 서브넷의 노드 간 최적화된 통신 지원

```
Type: "vxlan"
VNI: 1
Port: 8472
GBP: false
DirectRouting: false

```

### host-gw (호스트 게이트웨이)

host-gw는 원격 노드 IP를 통해 서브넷으로 IP 라우트를 생성합니다:

- 레이어 2 연결이 직접 가능한 환경에서 사용
- 캡슐화가 없어 VXLAN보다 성능이 우수
- 모든 노드가 동일한 L2 네트워크에 있어야 함
- 클라우드 환경에서는 일반적으로 사용 불가

```
Type: "host-gw"

```

### UDP

UDP 백엔드는 VXLAN을 지원하지 않는 오래된 커널을 위한 대안으로 제공됩니다:

- UDP 8285 포트 사용
- 사용자 공간에서 패킷 처리로 성능이 저하됨
- 디버깅 목적으로만 권장

```
Type: "udp"
Port: 8285

```

### WireGuard

WireGuard 백엔드는 노드 간 통신을 암호화하여 보안을 강화합니다:

- 커널 내장 WireGuard를 사용하여 패킷 암호화
- UDP 51820 포트 사용 (IPv6는 51821)
- PSK(Pre-Shared Key) 옵션으로 보안 강화

```
Type: "wireguard"
ListenPort: 51820
ListenPortV6: 51821

```

## Flannel의 네트워크 구성 요소

### cni0 브리지

cni0 브리지는 파드 간 통신을 위한 핵심 구성 요소로, 다음과 같은 역할을 합니다:

1. **같은 노드 내에서의 파드 간 통신**
    - 새로운 파드가 생성되면 가상 이더넷 인터페이스(veth 쌍)를 파드에 연결
    - veth 페어의 반대쪽 끝은 cni0 브리지에 연결
    - 이 브리지를 통해 같은 노드에 있는 모든 파드가 레이어 2 네트워크에서 통신
2. **호스트 네트워크와의 연결**
    - cni0는 호스트의 네트워크 인터페이스와 연결
    - 파드들이 외부 네트워크 또는 클러스터 내의 다른 노드와 통신 가능
3. **트래픽 라우팅**
    - 같은 노드 내에서 파드 간 트래픽 처리
    - 다른 노드나 외부 네트워크로 향하는 트래픽을 올바른 인터페이스로 포워딩

### flannel.1 인터페이스

flannel.1 인터페이스는 VXLAN 백엔드에서 노드 간 통신을 위한 VTEP 역할을 합니다:

1. **다른 노드에 위치한 파드 간 통신**
    - VXLAN ID 1을 사용하는 VTEP 역할
    - 패킷의 인캡슐레이션과 디캡슐레이션 담당
2. **오버레이 네트워크 구현**
    - 물리적 네트워크 위에 가상 네트워크 구축
    - 서로 다른 노드에 있는 파드들이 같은 네트워크에 있는 것처럼 통신

### VXLAN 작동 방식

VXLAN(Virtual Extensible LAN)은 Flannel의 기본 백엔드로, 다음과 같이 작동합니다:

1. **VXLAN 캡슐화**
    - 원본 레이어 2 패킷을 VXLAN 헤더로 캡슐화
    - VXLAN 패킷은 UDP로 캡슐화되어 전송 (UDP 포트 8472 사용)
    - VNI(VXLAN Network Identifier)를 사용하여 가상 네트워크 식별
2. **VTEP(VXLAN Tunnel End Point)**
    - 각 노드의 flannel.1 인터페이스가 VTEP 역할 수행
    - VTEP은 패킷의 캡슐화와 디캡슐화를 담당
    - VTEP 간의 통신은 물리적 네트워크를 통해 이루어짐
3. **FDB(Forwarding Database)**
    - 각 노드는 FDB를 유지하여 대상 MAC 주소와 VTEP IP 매핑
    - 이를 통해 패킷이 올바른 대상 노드로 전달됨

## Flannel vs 다른 CNI 플러그인

### Calico와의 비교

|특성|Flannel|Calico|
|---|---|---|
|**네트워킹 모델**|레이어 3 오버레이 네트워크|레이어 3 BGP 라우팅|
|**성능**|중간|높음 (오버레이 없음)|
|**네트워크 정책**|지원하지 않음|지원함|
|**복잡성**|낮음|중간 - 높음|
|**확장성**|중간|높음|
|**구성 용이성**|매우 쉬움|중간|
|**사용 사례**|간단한 구성, 소규모 클러스터|대규모 클러스터, 네트워크 정책 필요 시|

Calico는 BGP(Border Gateway Protocol)를 사용하여 네트워크 패킷을 라우팅합니다. 이는 Flannel과 달리 오버레이 캡슐화를 사용하지 않아 성능이 더 우수하지만, 설정 및 유지 관리는 더 복잡합니다.

### Weave Net과의 비교

|특성|Flannel|Weave Net|
|---|---|---|
|**네트워킹 모델**|레이어 3 오버레이|메시 오버레이|
|**암호화**|지원하지 않음 (WireGuard 백엔드 제외)|지원함|
|**네트워크 정책**|지원하지 않음|지원함|
|**복원력**|중간|높음 (메시 토폴로지)|
|**리소스 사용**|낮음|중간|
|**구성 용이성**|매우 쉬움|쉬움|
|**사용 사례**|간단한 구성|암호화 필요, 복잡한 네트워크 토폴로지|

Weave Net은 각 노드 간에 메시 오버레이 네트워크를 생성하여 유연한 라우팅을 제공합니다. 또한 네트워크 암호화와 같은 추가 기능을 제공합니다.

### Cilium과의 비교

|특성|Flannel|Cilium|
|---|---|---|
|**네트워킹 기술**|VXLAN, UDP|eBPF|
|**성능**|중간|매우 높음|
|**네트워크 정책**|지원하지 않음|고급 L7 정책 지원|
|**관측성**|제한적|높음|
|**복잡성**|낮음|높음|
|**사용 사례**|간단한 구성, 테스트 환경|고성능, 마이크로서비스, 보안 중심|

Cilium은 eBPF(extended Berkeley Packet Filter) 기술을 사용하여 성능과 가시성을 크게 향상시키며, 레이어 7 수준의 네트워크 정책을 지원합니다.

## Flannel의 장단점

### 장점

1. **단순성**
    - 설치 및 구성이 매우 간단함
    - 기본 설정만으로도 대부분의 환경에서 잘 작동함
    - Kubernetes 배포 도구에서 기본 지원됨
2. **가벼운 자원 사용**
    - 단일 바이너리로 배포되어 시스템 리소스 소비가 적음
    - 최소한의 오버헤드로 운영 가능
3. **안정성**
    - 오래된 프로젝트로 많은 버그가 수정되고 안정화됨
    - 대부분의 환경에서 문제없이 작동함
4. **호환성**
    - 다양한 Kubernetes 배포판과 호환됨
    - 대부분의 클라우드 환경에서 작동함

### 단점

1. **기능 제한**
    - 네트워크 정책을 지원하지 않음
    - 고급 네트워킹 기능이 부족함
    - 암호화가 기본적으로 지원되지 않음 (WireGuard 백엔드 제외)
2. **성능 오버헤드**
    - VXLAN 캡슐화로 인한 약간의 성능 저하
    - Calico와 같은 비-오버레이 솔루션보다 성능이 낮음
3. **대규모 클러스터 제한**
    - 매우 큰 규모의 클러스터에서는 확장성 제한이 있음
    - 복잡한 네트워크 요구사항이 있는 경우 부적합할 수 있음
4. **문제 해결의 어려움**
    - 오버레이 네트워크로 인해 일반적인 네트워크 디버깅 도구만으로는 문제 해결이 어려울 수 있음

## 실제 구현 시나리오

### Flannel 설치 및 구성

Kubernetes 클러스터에 Flannel을 설치하는 방법은 다음과 같습니다:

```bash
Copy# Flannel 설치
kubectl apply -f <https://raw.githubusercontent.com/flannel-io/flannel/master/Documentation/kube-flannel.yml>

```

설치 후 각 노드에는 다음과 같은 구성이 생성됩니다:

- **/run/flannel/subnet.env**: 서브넷 정보 저장 파일
- **cni0**: 브리지 인터페이스
- **flannel.1**: VXLAN 인터페이스

서브넷 환경 파일의 예:

```
FLANNEL_NETWORK=10.244.0.0/16
FLANNEL_SUBNET=10.244.1.1/24
FLANNEL_MTU=65485
FLANNEL_IPMASQ=true

```

### 네트워크 패킷 분석

Flannel 네트워크에서의 패킷 흐름을 분석하면 다음과 같습니다:

### 같은 노드 내 통신 (cni0 인터페이스)

```
tcpdump -i cni0 -nn icmp

```

같은 노드의 파드 간 통신은 cni0 브리지를 통해 직접 이루어집니다. 패킷은 캡슐화 없이 전달됩니다.

### 노드 간 통신 (flannel.1 인터페이스)

```
tcpdump -i flannel.1 -nn icmp

```

다른 노드의 파드로 향하는 패킷은 VXLAN으로 캡슐화되어 flannel.1 인터페이스를 통해 전송됩니다. 이 패킷은 UDP로 캡슐화되어 있으며, 대상 노드의 flannel.1 인터페이스에서 디캡슐화됩니다.

### 외부 통신 (eth0 인터페이스)

```
tcpdump -i eth0 -nn icmp

```

물리적 네트워크 인터페이스(eth0)에서는 VXLAN으로 캡슐화된 UDP 패킷이 관찰됩니다. 이 패킷은 대상 노드의 IP로 전달됩니다.

### 실제 사용 사례

Flannel은 다음과 같은 상황에서 특히 유용합니다:

1. **개발 및 테스트 환경**
    - 간단한 구성으로 빠르게 설정 가능
    - 최소한의 리소스 소비로 효율적인 운영
2. **소규모 및 중규모 클러스터**
    - 단순한 네트워킹 요구사항을 가진 클러스터
    - 복잡한 네트워크 정책이 필요하지 않은 환경
3. **초기 Kubernetes 학습**
    - 쿠버네티스 네트워킹의 기본 개념 학습에 적합
    - 복잡한 설정 없이 빠르게 시작 가능
4. **기존 인프라와의 통합이 간단한 경우**
    - 오버레이 네트워크가 기존 네트워크 인프라와 충돌하지 않는 환경

## 결론

Flannel은 Kubernetes 클러스터에서 가장 단순하고 사용하기 쉬운 네트워크 솔루션 중 하나입니다. 기본적인 레이어 3 오버레이 네트워크를 제공하여 파드 간 통신을 가능하게 하며, 최소한의 설정으로 대부분의 환경에서 잘 작동합니다.

Flannel의 주요 장점은 단순성과 가벼운 리소스 사용으로, 특히 소규모 및 중규모 클러스터나 개발 환경에 적합합니다. 그러나 네트워크 정책, 고급 기능, 대규모 확장성이 필요한 환경에서는 Calico, Cilium과 같은 대안을 고려해야 할 수 있습니다.

Kubernetes 네트워킹의 기본 개념을 학습하거나 빠르게 클러스터를 설정하려는 경우, Flannel은 탁월한 선택입니다. 그러나 프로덕션 환경에서는 특정 요구사항과 제약 조건을 고려하여 적절한 CNI 플러그인을 선택하는 것이 중요합니다.

Flannel은 계속해서 발전하고 있으며, 향후 더 많은 기능과 성능 개선이 이루어질 것으로 기대됩니다. Kubernetes 생태계가 성장함에 따라 Flannel도 함께 발전하여 사용자의 네트워킹 요구사항을 더 효과적으로 충족시킬 것입니다.
