## 사용자명 가용성 확인의 문제점
사용자가 앱에 가입할 때 선택한 사용자명이 사용 가능한지에 대한 즉각적인 피드백을 기대한다. 간단해 보이지만, 사용자 기반이 커질수록 이 작은 기능의 성능이 주요 병목 현상이 될 수 있다.
- 초당 수천 건의 확인 요청
- 회원가입 캠페인 중 트래픽 급증
- 정확성 필수 (잘못된 "사용 가능" 결과 없어야 함)
- 사용자는 보통 작은 변형으로 여러 번 재시도함

이런 상황에서 데이터베이스에 과부하를 주지 않으면서 대규모로 처리할 수 있는 시스템을 어떻게 구축할 수 있을까?

## 5계층 아키텍처
Node.js, TypeScript 및 클라우드 기반 도구를 사용한 계층화된 사용자명 가용성 시스템으로, 속도, 확장성 및 정확성을 최적화했다.

### 계층 1: 초고속 "아니오"를 위한 블룸 필터
블룸 필터를 사용하여 존재하지 않는 사용자명을 빠르게 제외할 수 있다. 블룸 필터는 **거짓 부정**을 생성하지 않으므로, 사용자명이 시스템에 없다고 하면 확실하다.

```javascript
const mightExist = bloomFilter.has(username.toLowerCase());
if (!mightExist) return { available: true, source: 'bloom_filter' };
```

💡 요청의 **60% 가 여기서  1ms 미만**으로 처리된다.

### 계층 2: Redis 캐싱 (Aiven.io 제공)
존재할 가능성이 있는 사용자명의 경우 Redis 캐시를 확인한다. 이는 특히 자주 확인되는 이름에 대한 데이터베이스 쿼리를 크게 줄인다.
```javascript
const cacheResult = await redis.get(`username:${username}`);
if (cacheResult !== null) return { available: cacheResult === '0', source: 'redis' };
```

완전 관리형 Redis 인스턴스를 위해 **Aiven.io**를 사용한다. 수동 운영, 백업 또는 장애 조치 설정이 필요 없다.

### 계층 3: 제안을 위한 접두사 트라이
사용자명이 이미 사용 중인 경우, 인메모리 트라이를 사용하여 스마트한 제안을 제공한다.

```javascript
if (trie.search(username)) {
  return {
    available: false,
    source: 'trie',
    suggestions: trie.generateSuggestions(username),
  };
}
```

다음과 같은 기능에 적합하다
- 실시간 자동 완성
- 대체 제안 (`john123`, `john_doe` 등)

### 계층 4: 최종 판단을 위한 MongoDB
MongoDB는 신뢰할 수 있는 소스로 작동한다. 이전 계층에서 사용자명을 찾지 못한 경우에만 사용된다.

```javascript
const user = await db.collection('usernames').findOne({ username: username.toLowerCase() });
return { available: !user, source: 'database' };
```

`username` 필드에 인덱스를 사용하여 빠른 조회를 보장한다.

### 계층 5: 복원력을 위한 로드 밸런서
모든 것은 Node.js 인스턴스 간에 트래픽을 분산하는 간단한 라운드-로빈 로드 밸런서로 묶여 있다.

```javascript
const server = getNextServer(); // 라운드-로빈 전략
```

프로덕션에서는 이것을 NGINX나 클라우드 로드 밸런서로 대체할 수 있다.
