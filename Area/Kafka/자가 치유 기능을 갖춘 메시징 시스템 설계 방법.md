#kafka #recovery

이벤트 기반 또는 메시지 기반 시스템에서 프로듀서와 컨슈머는 종종 다른 속도로 작동한다. 그런데 프로듀서가 너무 빠르면 어떻게 될까? Kafka나 RabbitMQ 토픽이 컨슈머가 따라잡지 못해 가득 차면 어떻게 될까?

이 글에서는 내부적으로 어떤 일이 일어나는지 살펴보고, 이러한 불균형의 결과와 더 복원력 있는 시스템을 설계하는 방법에 대해 알아보겠다. 필요한 경우 Go 코드 스니펫을 사용할 것이다.

## 문제: 프로듀서 처리량 > 컨슈머 처리량
Kafka를 사용한다고 가정해보자. 프로듀서는 초당 10,000개의 메시지를 푸시할 수 있다. 컨슈머는 데이터베이스 쓰기나 외부 API 호출과 같은 다운스트림 처리로 인해 초당 2,000개의 메시지만 처리할 수 있다.

어떤 일이 일어날까?
- 브로커(Kafka 토픽)에 메시지가 쌓이기 시작한다
- 컨슈머 지연이 증가한다
- 결국 시스템 리소스(디스크, 메모리, CPU)가 스트레스를 받는다
- 보존 기간 임계값을 넘어가면 메시지 손실 위험이 있다
- 의존 서비스에서 재시도 폭풍이나 충돌 루프가 발생할 수 있다

이는 단순히 이론적인 우려가 아니라 분산 시스템에서 불안정성을 일으키는 가장 흔한 원인 중 하나다.

## 1. 큐가 무제한으로 증가한다
Kafka와 같은 메시징 시스템은 일정 시간 동안 메시지를 버퍼링할 수 있다. 하지만 무한하지 않다.

예를 들어 Kafka는 구성된 보존 기간(예: 7일) 동안 메시지를 저장한다. 컨슈머가 그 기간보다 오래 지연되면 메시지가 손실된다.

Prometheus를 사용하여 지연을 다음과 같이 모니터링할 수 있다.
```
kafka_consumer_lag{consumer_group="my-consumer", topic="orders"} 125000
```

이 메트릭은 백로그가 문제가 되기 전에 발견하는 데 도움이 된다.

## 2. 백프레셔와 메모리 압박
RabbitMQ와 같은 시스템은 백프레셔를 적용하기 시작한다. 반면에 Kafka는 (디스크 공간이 있는 한) 기꺼이 메시지를 받아들이지만 지연이 조용히 쌓일 수 있다.
Go에서 컨슈머는 버퍼링된 채널을 가질 수 있다.
```go
messageChan := make(chan Message, 1000)
```

메시지가 소비되는 속도보다 빠르게 들어오면 채널이 가득 차고 컨슈머 고루틴이 블록되거나 충돌할 수 있다.

## 3. 컨슈머 지연 메트릭은 컨텍스트 없이는 거짓말을 한다
컨슈머 지연만 모니터링하는 것은 충분하지 않다.

다음을 상호 연관시켜야 한다.
- 들어오는 메시지 속도(프로듀서 측)
- 컨슈머 처리량
- 큐 길이 / 오프셋 지연

예를 들어, 지연이 안정적으로 보이더라도 들어오는 속도가 증가하고 처리량이 증가하지 않았다면 여전히 뒤처지고 있는 것이다.

## 4. 이 상황에 대처하는 방법
이 상황을 처리하기 위한 엔지니어링 전략을 살펴보자.

### a) 프로듀서 조절
프로듀서가 내부적(제어 가능)이라면 속도 제한기를 추가하자.
```go
limiter := rate.NewLimiter(1000, 10) // 초당 1000개 메시지

for _, msg := range messages {
    if err := limiter.Wait(context.Background()); err != nil {
        log.Printf("Limiter wait failed: %v", err)
        continue
    }
    sendToKafka(msg)
}
```

이는 컨슈머가 압도되는 것을 방지하고 다운스트림 혼란을 피한다.
### b) 컨슈머의 수평적 확장
컨슈머는 파티션 전체에 걸쳐 수평적으로 확장될 수 있다.

Kafka에서는.
- 토픽을 여러 파티션으로 분할
- 동일한 컨슈머 그룹의 여러 인스턴스 실행
- Kafka가 그들 사이에 파티션을 분배

이는 다음과 같은 경우에 효과적이다.
- 컨슈머 로직이 무상태(stateless)인 경우
- 시스템이 작업을 안전하게 병렬화할 수 있는 경우

### c) 컨슈머 효율성 증가
컨슈머 로직을 프로파일링하고 최적화하자.
- 가능한 경우 배치 처리 사용
- DB 왕복 최소화
- 쓰기를 위한 대량 삽입 사용

예시(단순 vs 배치 처리):
```go
// 단순
for _, e := range events {
    db.Exec("INSERT INTO logs ...", e)
}

// 배치
db.Exec("INSERT INTO logs ...", batchedEvents)
```

### d) 데드 레터 큐(DLQ) 구현
느리거나 나쁜 메시지는 파이프라인을 막을 수 있다.
문제가 되는 메시지를 감지하고 처리하도록 컨슈머를 설계하자.

```go
if processingFails(msg) {
    publishToDLQ(msg)
    continue
}
```

이는 하나의 나쁜 이벤트가 전체 흐름에 영향을 미치는 것을 방지한다.

### e) 동적으로 프로듀서 일시 중지(가능한 경우)
프로듀서와 컨슈머가 제어 평면을 공유하는 경우 동적 피드백을 고려하자.
예를 들어,
- 컨슈머가 현재 지연 또는 큐 깊이를 푸시한다
- 프로듀서가 그에 따라 백오프하거나 속도를 줄인다

이는 시스템 경계를 넘어 구현하기 어렵지만 내부 파이프라인에서는 매우 효과적이다.
### f) 비동기 + 버퍼링된 컨슈머
일시적인 스파이크를 처리하기 위해 컨슈머에 버퍼를 사용하자.
```go
buffer := make(chan Message, 10000)

go func() {
    for msg := range buffer {
        go handle(msg)
    }
}()
for {
    msg := <-kafkaConsumerChan
    select {
    case buffer <- msg:
        // ok
    default:
        log.Println("Buffer full, dropping message or triggering alert")
    }
}
```

주의해야 할 점은 이것이 단기간 스파이크에만 도움이 되며 장기적인 처리량 불일치에는 도움이 되지 않는다.

## 5. 메시지를 버려야 할 때(최후의 수단)
메시지 손실이 허용된다면(예: 원격 측정, 로그) 시스템을 과부하시키는 것보다 메시지를 버리는 것이 더 나을 수 있다.

경계가 있는 큐 + 가장 오래된 것 버리기 또는 가장 새로운 것 버리기 전략을 사용하자.

```go
select {
case buffer <- msg:
    // 처리
default:
    // 버리기 또는 알림
}
```

무음 실패를 피하기 위해 항상 드롭에 대해 알림을 설정하자.
## 마치며
프로듀서와 컨슈머 간의 균형은 분산 시스템에서 근본적인 관심사다.

**핵심 내용**
- 양쪽 끝을 모니터링하자: 생산 속도와 소비 지연
- 백프레셔, 속도 제한 또는 스케일링 적용
- 복원력을 위한 설계: 배치 처리, 버퍼링 및 나쁜 데이터 오프로딩
- 컨슈머 지연을 무시하지 말자

이 불균형에 대한 계획을 세우지 않는 것은 빠르게 복합되는 설계 부채다. 느린 컨슈머는 단순히 비효율적인 것이 아니라 규모에서는 재앙이 될 수 있다.
